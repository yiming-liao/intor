# Release notes template

Use this template for English GitHub Release notes. It complements the
per-package changelogs generated by Changesets and follows the structure of
Intor's existing releases. It is a manually applied template, not an
automatically loaded GitHub configuration file.

## Authoring rules

- Set the GitHub Release title to the primary package's exact tag, such as
  `intor@2.10.0`. For a CLI-only release, use its CLI tag. Preserve historical
  tag names; do not rename them to match the new convention.
- A coordinated release can have one set of notes covering several packages.
  Packages retain independent versions and tags.
- Read every relevant package changelog entry since the previous GitHub
  Release. Cross-check the tag comparison and release commit, especially when
  intermediate npm versions had no GitHub Release or predate the changelogs.
- Write for consumers: describe observable behavior, who is affected, and any
  action required. Do not paste raw commit logs or internal build output.
- Keep Summary to one or two sentences. Lead with significant behavior changes.
- Keep only applicable change categories. Use Added, Changed, and Fixed for
  common releases; add Deprecated, Removed, or Security when needed. Mention
  affected package names when the scope is not obvious.
- Label incompatible changes explicitly as **Breaking change** or
  **Behavior change**, regardless of the version bump. A minor-version policy
  exception must be explained in Notes, not presented as full compatibility.
- Include Migration whenever consumers must act, or must opt in to retain
  previous behavior. Give the affected versions and concrete steps. Add
  before/after examples when helpful; examples must match the shipped APIs.
  Use four-backtick fences for code blocks.
- Related packages lists only other packages actually published in this batch,
  with exact versions and a short explanation. Omit it for a single package.
- Notes is for relevant compatibility limits, known issues, and version-policy
  exceptions. Do not claim consent compliance or universal compatibility
  without evidence.
- Remove unused sections, template instructions, and all placeholders. Keep
  the remaining sections in the order below. Avoid duplicating the same detail
  across Summary, change bullets, and Notes.

## Copyable release body

Copy the content between the markers, excluding the markers themselves.
Replace all `{{...}}` placeholders and remove optional sections without content.
The Migration placeholder is prose: replace it with actionable instructions
and complete examples where necessary.

<!-- release-body:start -->

## {{primary-package}}@{{version}}

### Summary

{{Describe the main consumer-facing outcome. Highlight significant behavior changes.}}

### Added

- {{Package or feature: describe the new capability.}}

### Changed

- {{Package or setting: describe the previous and new behavior, and who is affected.}}

### Fixed

- {{Package: describe the failing scenario and the corrected behavior.}}

### Migration

{{Identify affected users or versions, explain the required action, and show how to preserve previous behavior when applicable.}}

### Related packages

| Package | Version | Change |
| --- | --- | --- |
| `{{related-package}}` | `{{version}}` | {{Explain the change or dependency update.}} |

### Notes

- {{Relevant limitation or explicitly agreed version-policy exception.}}

<!-- release-body:end -->

## Review before publication

- Confirm that the selected tag points to the intended release commit.
- Verify that listed package versions are available on npm before describing
  them as released; keep unfinished notes as a draft.
- Check migration examples against the released API and configuration defaults.
- Verify links and package versions, and remove every unused heading and placeholder.
- Keep GitHub Release creation separate from npm publication. Follow the
  [release guide](releasing.md); maintainers perform publication manually.
